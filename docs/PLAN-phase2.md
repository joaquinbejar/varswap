# varswap: phase 2 plan (devnet)

Scope given by the SOLANA-PROJECTS coordinator (2026-11-03, bus #51620):

1. a rolling public realized volatility index (1d, 7d, 30d) from the windows, published as
   files and JSON plus a CLI command, with quality labels (missed samples, degraded windows);
2. per-sample keeper fees: a design (ADR) first; if it changes the program, a verifiable
   build, a devnet upgrade and an upgrade drill;
3. the varswap section of the shared read-only dashboard, and its shell, which varswap owns:
   a static site (GitHub Pages or a local file, no backend) generated by a script that reads
   devnet and writes JSON, in a format agreed with metalbook and quotebook.

Devnet only: no mainnet action in any milestone. Hermes quota unchanged: varswap keeps 3
requests per minute across its processes (decision 2 of `docs/PLAN-improvements.md`), and
nothing in this plan adds a Hermes request. The index, the records and the dashboard read the
chain only.

Each milestone is one branch and one PR. `make pre-push` passes before every push, CI is green
on the head, codex reviews every PR before merge, and the coordinator gets a report at each
merge. Global rules apply (signed commits, English, checked arithmetic, no panics outside
tests, `MAJOR.MINOR` dependencies, no new dependency without approval).

State at the start (main `f5d5c7c`):

- The program has no fee path. `sample` is permissionless: any signer may pay for the
  transaction, the program reads no signer at all (`program/src/processor.rs`, `sample`), and
  the keeper's payer `5MTV…` bears the transaction fees and the Pyth posting costs.
- The hourly series runs since 2026-11-02 17:00Z: daily windows on SOL/USD, 17:00Z to 17:00Z,
  25 buckets of 3,600 s, created by `com.varswap.roll.devnet-roll` (PR #42) and sampled by
  `com.varswap.keeper.devnet-hourly`, watched by `com.varswap.watch.devnet-watch`
  (`docs/devnet.md`, "Daily hourly series").
- I7 records exist per window (`varswap-admin export-window`, `verify-window`,
  `window-table`; `docs/windows/`) with labels `complete`, `compressed`, `degraded`, `unknown`.
  Two are committed (the demo window and `7s5K`), neither in the series.

## P1. Realized volatility index

### The series

The index is defined on one **series**: a feed, an anchor hour, an interval and a first start,
written in `docs/index/series/sol-usd-hourly.json`:

```json
{ "feed": "ef0d8b6f…b56d", "anchor_hour": 17, "interval": 3600,
  "first_start": "2026-11-02T17:00:00Z", "program_id": "BWqs…xrB9", "cluster": "devnet" }
```

Day `d` of the series is the window with `start = first_start + d × 86400`,
`end = start + 86400`; its address is derived from that spec
(`varswap-admin window-address`), so the index needs no list of windows and nobody chooses
which windows enter it. Windows outside the spec (the demo window, `7s5K`, drill windows) are
never part of the series.

### The value

For a period of `k` days (`k` in {1, 7, 30}) ending with day `D`, the index uses the windows
of days `D − k + 1` to `D`. The days are aligned and contiguous: window `d` ends exactly where
window `d + 1` starts, so the spans neither overlap nor leave a gap. The two prints at a shared
boundary are separate samples (one per window), and the return between them is not counted:
each window's `sum_sq` covers its own 24 returns.

- Over the usable windows `U` of the period (below):
  `RV_k = (Σ_{i∈U} sum_sq_i) × YEAR_SECONDS / (Σ_{i∈U} span_i)`, computed with
  `varswap-core`'s `LnKernel::annualize` on the summed raw `sum_sq` (checked `u128`
  addition), so `RV_1` of a finalized window equals the `realized_var` stored in its account
  byte for byte. The volatility is `σ_k = sqrt(RV_k)`, an integer square root in the kernel's
  Q64.64 units rounded down, printed with 12 decimals; no floating point anywhere.
- Usable means: a finalized window whose record verifies (offline, and with `--rpc` when the
  record is first exported), with label `complete` or `compressed`. A `degraded` window has
  no realized variance (it settles as `Unwind`), an `unknown` one has an unproven history, and
  a missing day (no window at the derived address, or not final yet) has nothing; none of
  them enters the sums.
- So `RV_k` is the variance per unit time of the days that are usable, not of the period: a
  missing day is excluded, never interpolated or counted as zero.

### Quality labels

Each value carries:

- `days`: `k`; `usable`: the number of usable windows; `excluded`: per excluded day, its
  window address and reason (`degraded`, `unknown`, `missing`, `open`);
- `missed_samples`: the buckets the series did not sample on time, summed over the usable
  windows: in each compressed run of `m` buckets, `m − 1` of them (the print that filled
  them came after their boundaries), plus the count and longest of the compressed runs;
- `label`:
  - `complete`: every day usable, every window `complete`;
  - `compressed`: every day usable, at least one compressed run;
  - `partial`: at least one day excluded and `usable ≥ ceil(k / 2)`; the value is published
    with its exclusions;
  - `insufficient`: `usable < ceil(k / 2)` (for `1d`: no usable window); no value, only the
    exclusions.

The `ceil(k / 2)` threshold is a proposal for the coordinator (open question 1).

### Records for the series

The index reads I7 records, not the raw chain, so every value can be recomputed offline from
committed or published files. `varswap-admin series-sync <series.json> --out <dir>`:

- derives the addresses of days `0` to `D` (the last day whose `end + backfill_deadline` has
  passed, so the window can no longer change);
- for each day without a record in `<dir>`: reads the account (finalized commitment). Missing
  account: writes a `missing` stub (address, day, the read slot). Otherwise exports the
  record (`export-window`), runs `verify-window --rpc` on it, and writes it only if it
  verifies;
- leaves existing records untouched (a record of a final window never changes), so a rerun
  does no RPC beyond the account reads of the days still lacking a record.

### CLI and files

- `varswap-admin vol-index <series.json> --records <dir> [--day D] [--json]`: verifies every
  record offline, then prints the 1d, 7d and 30d values for day `D` (default the last day with
  a record): `RV`, `σ`, the label and the quality fields.
- `varswap-admin vol-index … --history --json`: one entry per day, for the dashboard and the
  published file.
- Published files: `index/sol-usd-hourly/records/<day>-<address>.json` (the records and
  stubs) and `index/sol-usd-hourly/index.json` (the history, with the series spec, the
  generator commit, `generated_at` and the newest slot read). Where they live is P4.

### Tests

- Exactness: `RV_1` of each committed record equals its account's `realized_var`; `RV_k` over
  synthetic records equals a direct recomputation of `Σ sum_sq × YEAR / Σ span`.
- Labels: one test per label and per exclusion reason, the threshold edges (`k = 7`: 4 usable
  is `partial`, 3 is `insufficient`), and `missed_samples` on a record with runs of 1, 3 and 5
  buckets (expected 0 + 2 + 4).
- Negative controls: a record that fails offline verify is rejected by `vol-index` (not
  silently excluded: the command fails and names the file); a record of a window outside the
  series spec (wrong address for its day) is rejected; a `missing` stub for a day whose
  account exists fails `series-sync --check` against a fake cluster.
- `series-sync` against the fake cluster used by `cli/tests/record.rs`: a missing day, an open
  day, a degraded day, an idempotent rerun with zero exports.

*Done when* the tests pass, `series-sync` has produced the records of the series' finalized
days on devnet, each verifies with `--rpc`, and `vol-index` prints the values for the latest
day with the expected labels (in the first days, `7d` and `30d` are `partial` or
`insufficient` by construction, and the output says so).

## P2. Keeper fees: ADR, then (if accepted) the program change

### P2a. ADR 0002 (document only)

`docs/adr/0002-keeper-fees.md`, reviewed by codex and decided by the coordinator before any
code. It must answer, with numbers:

- **Cost to cover**: the measured cost of one sample on devnet from the keeper's logs and
  `5MTV…`'s balance history: transaction fees of the post, sample and close transactions,
  the encoded VAA and price update rent (reclaimed or not), per bucket and per day.
- **Who funds it**. Options: the window creator prepays at `create_window` (a fee per bucket
  times the bucket count, held in the window account above its rent or in a vault PDA);
  swap openers pay into the window's pool at `open_swap`; no on chain fee (the operator
  pays, recorded off chain). For each: who bears it, what happens to the unspent part
  (refund to whom, and when: windows have no close instruction today), and the effect on
  accounts already on devnet.
- **What is paid**: per newly filled bucket, or per `sample` call that fills at least one
  bucket. A compressed run fills `m` buckets with one late print; paying per bucket would pay
  more for lateness, paying per call does not. The ADR picks one and says why.
- **To whom, without breaking canonicity** (`docs/PLAN.md` 4.1: the pusher has no choice of
  print). A fee changes nobody's choice of print, but it creates a race for the fee: anyone
  may call `sample` with a `PriceUpdateV2` account somebody else posted, so a copier who only
  watches the mempool could take the fee of the keeper who paid for the post. Candidate rule:
  the fee goes to the update's `write_authority` (`pyth-lite` already decodes it,
  `pyth-lite/src/update.rs`), so only the poster can be paid; the ADR checks this against the
  receiver's rules (who may be write authority, whether it can be set to another key).
- **Layout and compatibility**: new fields mean `WINDOW_VERSION` 2; the loader must keep
  reading version 1 windows (the live series) with no fee; the bucket bitmap, `sum_sq` and
  settlement are unchanged. Account sizes and the 10,240 byte creation cap rechecked.
- **Abuse**: a self-dealing creator and keeper (funds move between the same owner, no harm);
  dust fees; a fee larger than the cost (an incentive to fill late? no: canonicity fixes the
  price, and a bucket can be filled only once); rent and lamport arithmetic checked, with the
  rounding direction stated.
- **Decision**, alternatives rejected, consequences, and what would reopen it.

*Done when* codex approves the ADR and the coordinator rules on it (adopt with a program
change, or adopt "no on chain fee").

### P2b. Implementation (only if P2a adopts a program change)

- `varswap-core` and `program`: the fee fields and the transfer in `sample` (and the funding
  and refund paths the ADR picks), checked arithmetic, explicit rounding, a negative test per
  new account rule (forged vault, wrong recipient, a version 1 window paying nothing), and the
  existing suite unchanged on version 1 windows. Conservation: lamports in equals fees paid
  plus refund plus what remains, in a proptest and in the `swap_conservation` style fuzz
  target extended to fees.
- `sdk`, `keeper` (passes the new accounts; records the fee received), `varswap-admin`
  (`create-window` with the fee option; `show-window` prints it), `varswap-watch` (a fee pool
  running low is an alert, if the ADR has a pool).
- `docs/benchmarks.md` regenerated: every instruction's CU, `sample` with and without a fee.
- Verifiable build: the new build hash recorded in `docs/verifiable.md` (CI's `verifiable`
  job), and the audit scope recount (`docs/audit-scope.md`: lines, hashes, invariants).
- Devnet upgrade with the I2 upgrade authority, as rehearsed in I2: write buffer, check the
  buffer hash against the build hash after finalization, set the buffer authority, upgrade,
  then `get-program-hash` equals the build hash. Deploy output is captured only through an
  allowlist (the buffer recovery phrase).
- Upgrade drill, recorded in `docs/devnet.md`: the live series keeps sampling across the
  upgrade (version 1 windows, no fee, no missed bucket attributable to the upgrade); a new
  version 2 window with a fee is created, sampled hourly for a day by the keeper, and
  finalized; fees paid equal the expected count; a copier test on devnet (a second key calling
  `sample` with the keeper's posted update) gets no fee; the refund path runs once.
- *Done when* the tests and fuzz controls pass, the deployed hash equals the build hash, and
  the drill's numbers are in `docs/devnet.md`.

## P3. Shared dashboard: format, shell and varswap section

### P3a. The section format (agreed with metalbook and quotebook)

`docs/dashboard.md` defines `section.json`, version 1, proposed to the metalbook
(`joaquin/s-31f741ef51c4`) and quotebook (`joaquin/s-e3613763b15f`) sessions on the bus and
merged only with both ACKs:

```json
{
  "schema": "solana-projects-dashboard/section/1",
  "repo": "varswap",
  "title": "varswap: realized volatility",
  "cluster": "devnet",
  "generated_at": "2026-11-04T18:05:00Z",
  "source": { "commit": "<git sha>", "slot": 0, "program_ids": ["BWqs…"] },
  "status": { "level": "ok", "message": "" },
  "tiles": [ { "id": "rv-7d", "label": "SOL/USD σ 7d", "value": "0.512345678901",
               "unit": "annualized", "quality": "partial", "note": "6/7 days" } ],
  "series": [ { "id": "sigma-1d", "label": "σ 1d", "unit": "annualized",
                "points": [["2026-11-03T17:00:00Z", "0.498765432109"]],
                "quality": ["complete"] } ],
  "tables": [ { "id": "windows", "columns": ["day", "window", "label"],
                "rows": [["2026-11-02", "7ywX…", "complete"]] } ],
  "links": [ { "label": "records", "href": "index/sol-usd-hourly/" } ]
}
```

- Numbers are decimal strings (no float rounding between repos); times are RFC 3339 UTC;
  `status.level` is `ok`, `warn` or `stale`; `quality` is free text per repo, shown as a
  badge. Unknown fields are ignored, so a repo can add fields without breaking the shell; a
  breaking change bumps the version and the shell renders each version it knows.
- `sections.json` (owned by the shell) lists the sections: `[{ "repo", "url" }]`, each URL
  the repo's published `section.json`.
- A JSON Schema for version 1 in `docs/dashboard/section-1.schema.json`; each repo validates
  its own output against it in its CI (a test with the `serde_json` already in the workspace,
  no new dependency).

### P3b. The shell

- `site/`: `index.html`, `dashboard.js`, `dashboard.css`, hand written, no framework, no
  build step, no CDN, no external font, no analytics. It fetches `sections.json` and each
  section, renders tiles, series (inline SVG lines), tables and links, and shows per section
  its `generated_at`, its status and an error card when a section cannot be fetched or does
  not parse (one broken section never blanks the page). It reads nothing but those JSON
  files: no RPC from the browser.
- Works from a local directory (`python3 -m http.server` or any static server; a `file://`
  page cannot fetch, which the README says) and from GitHub Pages.
- Test: `make dashboard-check` validates every fixture section against the schema and checks
  that `index.html` references only files under `site/`; CI runs it.

### P3c. The varswap section

`scripts/dashboard.sh <out-dir>`: runs `series-sync` and `vol-index --history --json` (P1),
then writes `<out-dir>/varswap/section.json` (tiles for σ 1d, 7d and 30d with their labels;
series for the three σ histories; the windows table; links to the records) and copies the
shell. It reads devnet through the public RPC, holds no key, and makes no Hermes request.
`status` is `stale` when the newest final day is older than 48 h, `warn` when any 7d day is
excluded.

*Done when* both repos have ACKed the format, the shell renders the varswap section plus a
fixture section per sibling repo, a section that fails to load shows its error card, and the
generated JSON validates in CI.

## P4. Publication

Proposal (open question 2), GitHub Pages from a scheduled workflow, because the repos are
public, the generator needs no secret, and the coordinator asked for no backend:

- `.github/workflows/dashboard.yml`: daily at 18:30Z (after the roll window's end at 17:00Z,
  plus margin for the last bucket and finality), and on `workflow_dispatch`. It checks out
  main, builds `varswap-admin` (locked), fetches the current Pages content (the records
  already published), runs `scripts/dashboard.sh` against devnet's public RPC, and deploys the
  result with the official Pages actions pinned by SHA. Token permissions: `pages: write`,
  `id-token: write`, `contents: read`; no secrets.
- Records are append only: the workflow never rewrites a published record, and it fails (no
  deploy) if an existing record would change.
- Records are also committed to `docs/windows/` monthly by a normal PR, so the repo keeps a
  reviewable copy independent of Pages.
- Fallback with no Pages: the same script under a LaunchAgent writes the site into
  `~/.local/share/varswap-keeper/dashboard/`, served locally.
- The shell's `sections.json` points at each repo's Pages URL; GitHub Pages serves with
  `Access-Control-Allow-Origin: *`, so one page can fetch the siblings' sections (checked on
  the first deploy, and recorded).

*Done when* the workflow has run on schedule twice, the published index equals a local
`vol-index` run on the same records, and the page shows the three sections.
